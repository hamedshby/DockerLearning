Bind Mount چیست؟

Bind Mount یک فایل یا پوشهٔ مشخص از سیستم میزبان را مستقیماً داخل Container در دسترس قرار می‌دهد. مسیر مبدأ را شما انتخاب می‌کنید و Docker محتوای آن را مدیریت نمی‌کند.

اصل مهم

میزبان و Container به یک دادهٔ مشترک دسترسی دارند؛ تغییر از هر طرف برای طرف دیگر قابل مشاهده است. 

Host
└── /home/user/project
          │
          │  Bind Mount
          ▼
Container
└── /app

Bind Mount چه زمانی کاربرد دارد؟

  • اشتراک‌گذاری کد منبع با Container در محیط Development
  • تزریق فایل‌های پیکربندی بدون ساخت دوبارهٔ Image
  • دسترسی Container به فایل‌های ورودی یا خروجی موجود روی میزبان
  • مشاهدهٔ سریع تغییرات فایل‌های میزبان داخل Container
انتخاب مناسب

Bind Mount برای فایل‌هایی مناسب است که باید مستقیماً روی میزبان دیده یا ویرایش شوند؛ دادهٔ ماندگار برنامه معمولاً بهتر است داخل Volume قرار گیرد.

ساختار مسیر در Bind Mount 

host-path:container-path[:options]
بخش معنا نمونه
Host Path فایل یا پوشهٔ واقعی روی میزبان /home/user/site
Container Path محل نمایش داده داخل Container /usr/share/nginx/html
Options گزینه‌هایی مانند ro برای دسترسی فقط‌خواندنی ro

اتصال Bind Mount به Container

برای ساخت Bind Mount می‌توان از گزینهٔ کوتاه -v یا گزینهٔ صریح‌تر --mount استفاده کرد.

روش کوتاه با -v 

docker run -d \
  --name bind-web \
  -p 8080:80 \
  -v "$(pwd)/site:/usr/share/nginx/html" \
  nginx

پوشهٔ site از مسیر جاری میزبان داخل /usr/share/nginx/html در Container نمایش داده می‌شود.

روش صریح با --mount 

docker run -d \
  --name bind-web \
  -p 8080:80 \
  --mount type=bind,source="$(pwd)/site",target=/usr/share/nginx/html \
  nginx
-v --mount
کوتاه و مناسب اجرای روزمره خواناتر و صریح‌تر برای اسکریپت‌ها
ممکن است مسیر مبدأ ناموجود را به‌صورت پوشه بسازد. برای مسیر مبدأ ناموجود با خطا متوقف می‌شود.
Best Practice

در اسکریپت‌ها و محیط Production از --mount استفاده کنید.

Bind Mount فقط‌خواندنی

Bind Mount به‌صورت پیش‌فرض قابل‌نوشتن است. برای محدودکردن دسترسی از ro یا readonly استفاده کنید.

فقط‌خواندنی با -v 

docker run --rm \
  -v "$(pwd)/config:/app/config:ro" \
  alpine \
  cat /app/config/app.conf

فقط‌خواندنی با --mount 

docker run --rm \
  --mount type=bind,source="$(pwd)/config",target=/app/config,readonly \
  alpine \
  cat /app/config/app.conf

توسعهٔ زنده با Bind Mount

در محیط Development می‌توان کد پروژه را داخل Container Mount کرد تا تغییر فایل‌های میزبان فوراً در دسترس برنامه باشد. 

docker run --rm -it \
  -p 3000:3000 \
  -v "$(pwd):/app" \
  -w /app \
  node:22 \
  npm run dev
نکتهٔ وابستگی‌ها

Mount کردن کل پروژه ممکن است مسیرهایی مانند node_modules را بپوشاند؛ وابستگی‌ها را جدا نگه دارید یا فقط مسیرهای لازم را Mount کنید.

مقایسهٔ Bind Mount و Docker Volume

ویژگی Bind Mount Docker Volume
مدیریت مسیر مسیر دقیق را کاربر انتخاب می‌کند. Docker محل ذخیره‌سازی را مدیریت می‌کند.
وابستگی به میزبان به مسیر و سیستم‌عامل میزبان وابسته است. مستقل‌تر از مسیر میزبان است.
کاربرد پیشنهادی کد منبع، پیکربندی و فایل‌های میزبان دادهٔ ماندگار برنامه و دیتابیس
مدیریت با Docker CLI فرمان مستقل create یا inspect ندارد. با docker volume مدیریت می‌شود.

Bind Mount در Docker Compose

نحو کوتاه

services:
  web:
    image: nginx
    ports:
      - "8080:80"
    volumes:
      - ./site:/usr/share/nginx/html:ro

نحو بلند و صریح 

services:
  web:
    image: nginx
    volumes:
      - type: bind
        source: ./site
        target: /usr/share/nginx/html
        read_only: true

مسیر نسبی در Compose نسبت به پوشهٔ فایل Compose محاسبه می‌شود.

مسیر میزبان و تفاوت سیستم‌عامل‌ها

  • در Linux و macOS می‌توان از $(pwd) برای مسیر جاری استفاده کرد.
  • در PowerShell از ${PWD} یا مسیر کامل مانند C:\project استفاده کنید.
  • مسیرهایی که فاصله دارند باید داخل علامت نقل‌قول قرار گیرند.
  • Permission و مالکیت فایل روی Linux می‌تواند دسترسی Process داخل Container را محدود کند.
رفتار مهم مقصد

Bind Mount فایل‌های قبلی مسیر مقصد را حذف نمی‌کند، اما تا زمانی که Mount فعال است آن‌ها را می‌پوشاند.

امنیت و بهترین روش‌ها

  • فقط فایل‌ها و پوشه‌های ضروری را Mount کنید؛ ریشهٔ سیستم میزبان را در اختیار Container قرار ندهید.
  • برای فایل‌های پیکربندی و محتوای ثابت از حالت فقط‌خواندنی استفاده کنید.
  • فایل‌های حساس مانند کلید خصوصی، فایل env و Docker socket را بدون نیاز قطعی Mount نکنید.
  • Container را با کاربر غیر root اجرا کنید و Permission مسیر میزبان را هماهنگ کنید.
  • در Production مسیرهای مطلق، مشخص و پایدار به کار ببرید.
هشدار امنیتی

Mount کردن /var/run/docker.sock می‌تواند دسترسی بسیار قدرتمندی به میزبان بدهد و نباید بدون بررسی امنیتی انجام شود.

تمرین عملی: اجرای Nginx با Bind Mount

گام ۱: ساخت پوشهٔ سایت 

mkdir site

گام ۲: ساخت صفحهٔ HTML 

echo "<h1>Bind Mount Works</h1>" > site/index.html

گام ۳: اجرای Nginx 

docker run -d \
  --name bind-web \
  -p 8080:80 \
  --mount type=bind,source="$(pwd)/site",target=/usr/share/nginx/html,readonly \
  nginx

گام ۴: مشاهده در مرورگر 

http://localhost:8080

گام ۵: تغییر فایل روی میزبان 

echo "<h1>Updated without rebuilding</h1>" > site/index.html

گام ۶: پاک‌سازی Container 

docker rm -f bind-web
نتیجهٔ تمرین

تغییر فایل میزبان بدون Build دوباره نمایش داده می‌شود و حذف Container فایل میزبان را از بین نمی‌برد.

سؤالات تستی Bind Mount

  1. در Bind Mount مسیر مبدأ را چه کسی تعیین می‌کند؟

    1. Docker به‌صورت تصادفی
    2. کاربر یا مدیر سیستم
    3. Container Registry
    4. Dockerfile همیشه

    پاسخ صحیح: گزینهٔ ۲ — کاربر مسیر دقیق میزبان را مشخص می‌کند.

  2. کدام گزینه Bind Mount فقط‌خواندنی می‌سازد؟

    1. -v ./config:/app/config:ro
    2. -v ./config:/app/config:rw-only
    3. --mount type=volume,delete
    4. --read ./config

    پاسخ صحیح: گزینهٔ ۱ — پسوند ro دسترسی نوشتن را غیرفعال می‌کند.

  3. برای دادهٔ ماندگار دیتابیس معمولاً کدام انتخاب مناسب‌تر است؟

    1. Docker Volume
    2. فایل داخل لایهٔ Container
    3. قرار دادن داده در Dockerfile
    4. ذخیره در Image Tag

    پاسخ صحیح: گزینهٔ ۱ — Docker Volume برای دادهٔ ماندگار انتخاب مناسب‌تری است.

  4. اگر Bind Mount روی مسیری دارای فایل در Image قرار گیرد چه می‌شود؟

    1. فایل‌های Image برای همیشه حذف می‌شوند
    2. فایل‌ها هنگام فعال‌بودن Mount پوشانده می‌شوند
    3. Container اجرا نمی‌شود
    4. Docker یک Volume تصادفی می‌سازد

    پاسخ صحیح: گزینهٔ ۲ — فایل‌ها حذف نمی‌شوند اما موقتاً پوشانده می‌شوند.

  5. مزیت مهم --mount نسبت به -v برای مسیر مبدأ ناموجود چیست؟

    1. مسیر را بدون اطلاع حذف می‌کند
    2. با خطای واضح متوقف می‌شود
    3. Image را دوباره Build می‌کند
    4. Mount را به Volume تبدیل می‌کند

    پاسخ صحیح: گزینهٔ ۲ — --mount برای مسیر مبدأ ناموجود خطا می‌دهد.
