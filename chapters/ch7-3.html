پشتیبان‌گیری و بازیابی چیست؟

Backup یک نسخهٔ مستقل از داده است و Restore آن نسخه را به یک محل سالم و قابل استفاده برمی‌گرداند.

اصل ۳-۲-۱

سه نسخه از داده، روی دو نوع رسانه و دست‌کم یک نسخه خارج از میزبان اصلی نگه دارید. 

Application ──writes──▶ Docker Volume
                           │
                           │ backup
                           ▼
                    backup-2026-07-31.tar.gz
                           │
                           │ restore drill
                           ▼
                    New Docker Volume

چه چیزهایی باید پشتیبان‌گیری شوند؟

  • دادهٔ ماندگار داخل Volumeها و Bind Mountها
  • نسخهٔ منطقی دیتابیس
  • فایل‌های Compose و تنظیمات
  • متادیتای بازیابی
داده روش پیشنهادی دلیل
فایل‌های ثابت داخل Volume tar ساده و قابل حمل
دیتابیس در حال اجرا ابزار Native دیتابیس از تراکنش‌ها آگاه است
مسیر Bind Mount ابزار میزبان یا tar مبدأ روی میزبان است

تهیهٔ Backup سازگار

اگر برنامه هنگام کپی در حال نوشتن باشد، فایل‌های Backup ممکن است سازگار نباشند.

Backup فایل خام دیتابیس

فایل‌های زندهٔ دیتابیس را بدون هماهنگی مستقیم کپی نکنید.

پشتیبان‌گیری از Named Volume

یک Container موقت alpine با دستور tar محتوای Volume را فشرده می‌کند. 

docker run --rm \
  --mount source=app-data,target=/source,readonly \
  --mount type=bind,source="${PWD}/backups",target=/backup \
  alpine \
  tar -czf /backup/app-data-2026-07-31.tar.gz -C /source .
  • --rm کانتینر موقت را حذف می‌کند.
  • readonly از تغییر مبدأ جلوگیری می‌کند.
  • -C /source ساختار Archive را ساده نگه می‌دارد.

مشاهدهٔ محتویات Backup

docker run --rm \
  --mount type=bind,source="${PWD}/backups",target=/backup,readonly \
  alpine \
  tar -tzf /backup/app-data-2026-07-31.tar.gz

بازیابی Named Volume

Backup را ابتدا داخل یک Volume جدید بازیابی و آزمایش کنید. 

docker volume create app-data-restored

docker run --rm \
  --mount source=app-data-restored,target=/restore \
  --mount type=bind,source="${PWD}/backups",target=/backup,readonly \
  alpine \
  tar -xzf /backup/app-data-2026-07-31.tar.gz -C /restore
هشدار بازنویسی

برای Restore از مقصد خالی و ترجیحاً جدید استفاده کنید.

پشتیبان‌گیری از Bind Mount

مسیر Bind Mount را می‌توان با ابزار میزبان، Snapshot یا tar پشتیبان‌گیری کرد. 

tar -czf ./backups/site-2026-07-31.tar.gz -C ./site .

mkdir ./site-restored
tar -xzf ./backups/site-2026-07-31.tar.gz -C ./site-restored

بعد از Restore، Permission، مالکیت و Symbolic Linkها را بررسی کنید.

Backup منطقی SQL Server

SQL Server باید فایل سازگار .bak را با دستور Native خود بسازد. 

BACKUP DATABASE [ShopDb]
TO DISK = N'/var/opt/mssql/backup/ShopDb-full.bak'
WITH INIT, COMPRESSION, CHECKSUM;

بررسی فایل Backup در SQL Server 

RESTORE VERIFYONLY
FROM DISK = N'/var/opt/mssql/backup/ShopDb-full.bak'
WITH CHECKSUM;

RESTORE VERIFYONLY مفید است، اما جای Restore آزمایشی را نمی‌گیرد.

اعتبارسنجی Backup و آزمون Restore

  1. خروجی و کد خروج را ثبت کنید.
  2. اندازهٔ فایل را بررسی کنید.
  3. مقدار SHA256 checksum بسازید.
  4. Restore دوره‌ای را در محیط جدا تمرین کنید.
# PowerShell
Get-FileHash .\backups\app-data-2026-07-31.tar.gz -Algorithm SHA256

# Linux
sha256sum ./backups/app-data-2026-07-31.tar.gz
معیار واقعی

Backup آزمایش‌نشده، Backup قابل اعتماد نیست.

نگهداری، امنیت و خودکارسازی

  • سیاست Retention مشخص داشته باشید.
  • Backupها را رمزنگاری کنید.
  • دسترسی خواندن را محدود کنید.
  • Backup را خودکار و شکست آن را Alert کنید.
  • یک نسخهٔ خارج از میزبان و ترجیحاً Immutable داشته باشید.

چک‌لیست عملیاتی Backup

پرسش پاسخ مورد انتظار
RPO چقدر است؟ حداکثر دادهٔ قابل از دست رفتن
RTO چقدر است؟ حداکثر زمان بازیابی

تمرین عملی: Backup و Restore یک Named Volume

گام ۱: ساخت Volume و دادهٔ آزمایشی 

docker volume create lab-data
docker run --rm --mount source=lab-data,target=/data alpine \
  sh -c "echo 'order-1001' > /data/orders.txt"

گام ۲: ساخت پوشهٔ Backup 

mkdir backups

گام ۳: تهیهٔ Backup فقط‌خواندنی 

docker run --rm \
  --mount source=lab-data,target=/source,readonly \
  --mount type=bind,source="${PWD}/backups",target=/backup \
  alpine tar -czf /backup/lab-data.tar.gz -C /source .

گام ۴: ساخت مقصد و Restore 

docker volume create lab-data-restored
docker run --rm \
  --mount source=lab-data-restored,target=/restore \
  --mount type=bind,source="${PWD}/backups",target=/backup,readonly \
  alpine tar -xzf /backup/lab-data.tar.gz -C /restore

گام ۵: بررسی دادهٔ بازیابی‌شده 

docker run --rm --mount source=lab-data-restored,target=/data,readonly \
  alpine cat /data/orders.txt
نتیجهٔ تمرین

نمایش order-1001 یعنی داده داخل Volume جدید بازیابی شده است.

سؤالات تستی پشتیبان‌گیری و بازیابی

  1. چرا Volume روی همان میزبان Backup نیست؟

    • چون فقط‌خواندنی است
    • چون هر دو روی یک میزبان‌اند
    • چون Mount نمی‌شود
    • چون Docker آن را حذف می‌کند

    پاسخ صحیح: گزینهٔ ۲

  2. چرا از readonly استفاده می‌کنیم؟

    • برای جلوگیری از تغییر مبدأ
    • برای افزایش اندازه
    • برای حذف Container
    • برای غیرفعال کردن tar

    پاسخ صحیح: گزینهٔ ۱

  3. روش مطمئن‌تر برای دیتابیس در حال اجرا چیست؟

    • کپی فایل خام
    • ابزار Native دیتابیس
    • حذف Volume
    • تبدیل به tmpfs

    پاسخ صحیح: گزینهٔ ۲

  4. چگونه قابل استفاده بودن Backup را ثابت می‌کنیم؟

    • بررسی نام فایل
    • بررسی وجود Archive
    • Restore آزمایشی
    • تغییر نام Volume

    پاسخ صحیح: گزینهٔ ۳

  5. RPO چه چیزی را مشخص می‌کند؟

    • حداکثر دادهٔ قابل از دست رفتن
    • تعداد CPU
    • حجم Image
    • نام فایل Compose

    پاسخ صحیح: گزینهٔ ۱
